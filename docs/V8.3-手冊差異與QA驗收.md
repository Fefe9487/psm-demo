# V8.3 手冊差異與 QA 驗收紀錄

更新日期：2026-09-27。範圍為本地 `石化及化學工廠製程安全管理參考手冊-V8.3.docx` 與目前 demo／首次填報精靈。手冊封面標示「草案」；此紀錄不把草案直接視為現行法規。

## 一、先釐清適用層級

1. **產品邊界與階段**：依使用者決策，本階段只處理初次填報的 PSM 十四項，不製作或送出甲類申請書與安全衛生管理基本資料。場所名稱、範圍、部門等在十四項內作為引用主資料，不代表另建基本資料送件功能。日後製程修改或定期審查時，事業單位應以系統既有資料為起點重新檢視、更新並填寫當次資料；後續填報流程不在本階段冒充初次填報完成。
2. **現行法規對照**：[危險性工作場所審查及檢查辦法第 5 條](https://laws.mol.gov.tw/FLAW/FLAWDOC01.aspx?flno=5&id=FL015049)文字仍列申請書、安全衛生管理基本資料及附表一至十四；[製程安全評估定期實施辦法第 4 條](https://laws.mol.gov.tw/FLAW/PrintFLAWDAT0202.aspx?id=FL075606)列十四項。這是整體申請流程的法規背景，不納入本系統功能驗收；實際送審責任應由系統外流程處理。
3. **V8.3 草案**：是線上結構化欄位、附件與跨章引用的設計參考。手冊前言也明寫送審及檢附事項以現行法令和職安署審查要求為準。
4. **目前產品**：是本地示範與填報原型。畫面的「基本檢核通過」只表示目前程式已知欄位與附件條件通過，不能解讀為審查機構已接受。

PSM 十四項正式使用前須逐項比對現行法規附表原件及實際線上申報系統欄位，確認附件、簽認、表格格式及送件時點；不能只用 V8.3 草案或 demo 報表代替。

## 二、手冊組織結構

- 前言與總論：申報現狀、結構化資料、引導式填報、線上風險評估。
- 四階段：確定甲類場所邊界 → 建立 PSI → 填管理措施 → 變更／修正。
- 六項填報通則：來源表只維護一次；圖資含圖號、版次與日期；不得虛構設備類型或跳過承攬／動火；同文件同版次只上傳一次；程序與執行紀錄均須交代；是／否選否應說明原因。
- 附表一：先建 1.0-1 部門、1.0-2 製程、1.0-3 設備、1.0-4 化學品、1.0-5 區域，再填 1.1–1.11。這些主鍵供後續附表選用。
- 附表二至十四：PHA、勞工參與、SOP、訓練、承攬、PSSR、MI、動火、MOC、事故、緊急應變、稽核、商業機密。各章的原始程序、圖資或紀錄仍以附件保留。
- 附錄一列應填表。1.0-4-1／1.0-4-2、8.0-1、8.3-1／8.3-2是分類、資料庫或查詢參考，手冊明示不列申報應填表。

## 三、已修正並有回歸檢查的差異

- **2.2 → 2.4**：PHA 評估紀錄已具編號、方法、數量、日期及實際檔案；2.4 必須選同場所既有評估編號，設備須屬所選製程，且可複選。僅填檔名不算上傳。
- **6 → 11**：第十一章事故共通資料改用單一 `incident` 來源，承攬事故可引用；舊版 JSON 11.2 列於資料庫副本測試中移轉。被引用的事故不得直接刪除。
- **第六章零事故**：依使用者裁定，仍須登錄所有承攬商與期間。精靈新增名冊、逐筆事故關聯與「名冊已列齊」確認；零事故與已有事故的互斥也納入檢查。
- **4.1–4.4**：已存在的設備類型都須有 SOP，不能用「無該類型」聲明跳過；4.2–4.4 均納入基本檢核。移除畫面把 4.4 列錯放到 4.3 的重複顯示。
- **4.4 上下限方向**：依 1.5 的壓力、溫度、流量與組成參數逐項引用；超上限與低於下限各須填後果及矯正程序，或具體不適用理由。舊式合併列留待人員刪除重填，不自動拆解成未經確認的兩個方向。
- **1.5 實際數值門檻**：流量與組成補上操作下限及安全下限輸入。已有 1.5 參數列須有單位、至少一個有效操作範圍數值與至少一個有效安全界限數值；空白或示範占位列不再讓第一章顯示完成，也不能直接拿到 4.4 填偏移後果。
- **1.5 逐台檢討**：完整設備清單逐台記錄已選壓力／溫度／流量／組成項目，全部不適用要寫理由。每個已選參數的上下方向須分別有操作值與安全值，或具體不適用理由；單次操作量與單位、連續操作不適用理由已結構化。實際內容物逐筆關聯本製程化學品與 SDS；舊備註及舊內容物列保留，但未經逐台重新確認不算完成。
- **第 5 章逐份 SOP 覆蓋**：一門課可關聯同製程多份 SOP；每份 SOP 須有課程或具體例外理由。課程未關聯 SOP 須說明，初訓／複訓時數和複訓頻率須有值。舊資料單一 SOP 關聯在遷移時保留。
- **第 7 章逐台 PSSR 判定**：設備清單須逐台判定適用性；不適用與全場所無案件都須說明理由。適用設備須有檢查日期及紀錄；有改善建議的列須有預定日期與追蹤結果。無案件聲明與既有檢查紀錄互斥。
- **第 7 章無案件聲明**：全場所聲明不再跳過逐台適用性檢查；逐台均判不適用且附理由後，才能連同全場所理由交代無案件。
- **8.2 單一來源與彙總**：失效率已改用共用 `mi_failure` 表；舊 JSON 8.2 原文保留，只有可解析的實際數值會移入待確認列，占位文字不算完成。每台安全關鍵設備須填統計期間、有限且非負的運行小時與整數失效事件數；零時數須填原因且不算個別率。六大類彙總以失效事件總數除以運行小時總數，排除未確認與零時數列。
- **8.2 資料不足**：另設資料不足紀錄，可保存統計期間及具體原因，不使用假零值；頁面與報表顯示待人工確認，章節不自動通過基本檢核，失效率及同類彙總排除該設備。
- **8.1 逐台篩選**：完整設備清單新增安全關鍵性確認，填否須有依據；尚未篩選的設備會留在待補清單。
- **8.1 逐項檢查**：每台安全關鍵設備可有多筆損壞機制或功能檢查項目，每筆各自填檢查方式、頻率、程序書及同製程 P&ID；六大類由人確認並存於逐台篩選資料。舊 JSON 與舊 `mi_screen` 明細移至共用明細表；舊列保留原文並標示待確認，避免把多個損壞機制誤認成同一組方法。篩選仍以 `mi_screen` 為來源。
- **第十章 MOC 文件**：依使用者裁定，首次送件只要求一份管理 MOC 運作的程序書；「內部管理程序」與「變更管理計畫書」是手冊對同一文件的稱呼，文件庫可重複引用同版次。無變更案件仍須程序書；全新無案件、已有執行紀錄與「尚無案件」聲明不得互相矛盾。
- **第十章變更範圍**：一件變更可複選多個製程、設備及化學品；設備與化學品須屬所選製程，化學品同時引用 SDS，變更管理項次不得重複。舊式單一關聯列保留顯示，但未經重新確認不算完成。
- **第九章**：四個是／否答案不能代替動火管制區域；至少要有區域及防護原因。
- **12.2 數量**：器材數量與單位分欄，只彙總同名且同單位的列；數值、區域與頻率在存檔時檢查。
- **12.1 實際範圍**：緊急狀況可複選製程、設備、化學品與區域，設備／化學品須屬所選製程；沒有選設備或化學品須說明原因，集合點須選已標示的緊急集合區。舊式單一關聯列保留顯示並要求重新確認。
- **12.1 演練狀態**：每個緊急狀況均須填計畫涵蓋項目；已演練者填日期並上傳紀錄，未演練者填預定日期及原因，保留待人工確認，不自動讓章節顯示通過。
- **第 13 章首次申請**：手冊 13.1 說尚未執行首次稽核免填計畫，13.2 另說初次申請者免填最近兩次稽核結果。精靈已移除對首次申請的 13.2 強制列／零不符合聲明；自願登錄的改善事項仍須引用既有 13.1 項次並填措施、負責部門與期限，無首次稽核聲明不能與既有紀錄並存。
- **附件版次**：第 4–13 章目前有共用文件庫，記錄文件編號、名稱、修訂日期及實際檔案；同版次只能上傳一次，其他章節可引用。

- **已裁定：第六章零事故名冊**。手冊第六章前段寫承攬商與期間；6.2-1 允許「無事故據實註明」。使用者裁定即使零事故，仍須登錄所有承攬商。
- **已裁定：首次送件 MOC 文件**。架構段落的「內部管理程序」與 10.1 的「變更管理計畫書」指同一份管理 MOC 運作的程序書。第十章只要求上傳或引用一次，文件可跨章共用版次。
- **已裁定：1.5 全部不適用**。每台設備仍須檢討；沒有適用安全上下限項目時可全部不適用，但須填具體理由，不得留白自動通過。
- **已裁定：7.1 無案件**。全場所無案件聲明不能取代逐台適用性判定；全不適用時須有逐台理由及全場所理由。
- **已裁定：8.2 資料不足**。允許存統計期間與原因，失效率及同類彙總不計算該台，並維持待人工確認，不自動顯示基本檢核通過。
- **已裁定：12.1 尚未演練**。每情境記錄計畫涵蓋項目；已演練上傳紀錄，未演練填預定日期與原因並維持待人工確認。
- **已裁定：產品階段**。目前只做初次填報 PSM 十四項；後續製程修改與定期審查從系統既有資料重新填寫當次內容，不把舊資料自動視為新申報已確認。

## 六、QA 流程與案例

每次改欄位、資料關聯、附件或報告後：

1. 執行 `./qa.ps1`。它依序檢查 Python 編譯、pytest，以及兩個本地 SQLite 資料庫的**副本**遷移、外鍵與跨章引用。原始資料庫不會被 QA 腳本寫入。
2. 查看 `scripts/qa_v83.py` 輸出的十四章待補清單。HF 示範中的檔名、假設值與草稿應維持「待補」，不為求全綠而假造核准文件。
3. 跑 `tests/test_v83_cross_chapter.py` 的正反案例：11.2 事故可於 6.2 選取；零事故仍須有名冊；跨製程設備不可進 2.4；1.5 每台設備實際界限、單次操作量與內容物；4.4 上下限分方向；一門課可關聯多份 SOP、未涵蓋 SOP 留待補；7.1 無案件仍須逐台判定；8.1 多檢查項目與舊資料待確認、8.2 資料不足保留待人工確認且不虛構失效率；9.1 不能靠是／否跳過；MOC 無案件仍須程序書且多製程關聯不能跨製程；12.1 複選與跨製程驗證、演練已執行要附件、未執行保留待人工確認；13.2 首次申請免填而自願填寫須有稽核關聯；同版次文件跨章引用。
4. 用首次填報頁人工走一輪：建立核心清單 → 切到每章 → 新增／更正／刪除 → 檢查錯誤提示 → 預覽報告。至少用 HF 有事故案例及「多承攬商、零事故」案例各一次。
5. 對每一章另做官方附表欄位對照、附件原件與簽認檢核；由熟悉甲類場所申報與現場製程的人員簽核。QA 程式只查結構及已實作規則。

演示時應明示案例用途：HF 供料／卸收與尾氣鹼洗數字是教學假設；SDS、圖資、評估紀錄、程序全文、設備故障資料需要現場真實文件。使用「試用範例資料」後，待補清單就是演示後續補件路徑。

兩個獨立案例可直接啟動：

- `powershell -ExecutionPolicy Bypass -File scripts/run_demo_case.ps1 -Case hf-incident`：HF 密閉供料，含一筆承攬虛驚，展示 11.2 → 6.2 的事故共用。
- `powershell -ExecutionPolicy Bypass -File scripts/run_demo_case.ps1 -Case zero-accident-contractors`：同一製程背景、兩家承攬商、近五年零事故，展示名冊與零事故聲明的區別。

腳本會在 `data/demo_cases/` 建立固定案例資料庫，與日常 `psm_fill_hf.sqlite` 分開。第二次執行會沿用案例資料；要重新產生示範內容時，明確執行 `python scripts/build_demo_cases.py --force`。預設埠為 11506，可用 `-Port` 指定其他可用埠。
